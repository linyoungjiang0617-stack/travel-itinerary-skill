# 网站与数据架构

- 一个统一行程数据模型：旅行、日期、活动 ID、名称、地点及地址、时间模式、开始和时长、选择、费用、打卡及实际完成时间、预订准备、来源。支持增改删；固定航班等锚点不随弹性项目移动。用目的地本地时区计算；未加载时间时不误报过期。未打卡的过时事项提醒，不能自动完成。提前试打卡不应把未来行程移动到当前日期。
- 顶部根据实时本地时间和共享打卡显示当前／下一项，并提供该项导航和打卡入口；同步延迟及冲突应可见。实际完成可推动后续弹性安排，固定锚点冲突显式提示。所有设备共享同一数据源，版本号比较与原子写入防止并发覆盖；服务端校验输入、拒绝无效链接和负数。失败提示不得声称已保存。
- 对确认订单保护不被误改或重复计算；其他项目保留两人预估与实际支出，实际为零也要生效，人均仅用于展示计算，货币显示到分。分享前说明公开链接的可见和可编辑范围，以用户决定为准。
- 所有路线节点、酒店和餐饮候选提供导航；使用完整地点与地址，核对同名分店。可用时提供高德 App 路线与 HTTPS 地点搜索；微信内不要假定能唤起 App，提供网页版、复制完整地址与在浏览器中打开的指引，复制失败允许手动选中。未确定集合点先提示核对，不冒充准确定位。目的地不在中国时优先用户适用的当地地图。
- 旅行资料及航班时刻标注来源、核验时间，展示预计值和未确认事项。候选食物选择后的重复店或品类提示应按共享数据动态计算。提前准备提醒仅提示，不表示已经自动预约或取号。
- 线路示意采用清晰线性顺序，首页优先当前与接下来；五天总览、住宿、必玩／可选及费用明细等按旅行长短和用户偏好调整。不要重复写住宿切换、安排无意义的长时间回酒店休息；实际位置和行程优先于固定模板。
- 部署前先确认现有环境和访问设置，备份在线数据；数据迁移避免双写分叉。公网链接不是大陆可达的保证：域名本身不决定网络可达性，迁移必须考虑前端与共享后台、平台条件及备案，实测后才可确认。保持原网址除非用户明确要求改动。
- 验证覆盖真实状态：时间前／进行中／过时／全完成、固定事项冲突、两页同步和并发冲突、订单锁定、实际金额为零、所选餐厅目的地、各天每个导航入口、常见手机宽度及费用表。实测微信、iOS、Android 或大陆网络缺失时说明，别假装实现或将国外托管等同国内部署。
